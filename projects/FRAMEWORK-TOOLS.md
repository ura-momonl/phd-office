# 科研项目框架 工具与显示手册

按需查阅：要改 FRAMEWORK.md 结构、用 projects 命令、改看板显示或排错时读；日常整理研究内容不必通读。原则和底线在 FRAMEWORK-RULES.md。

## 日志写法细则

- 多种测量共用一次粗略叙述时，原记录只放在共同父栏一次，各方法保留自己的入口并引用原记录；不复制正文，也不拆出没有独立证据的实验记录。单条记录直接展开，不再套“详细日志”标题；有多个子项共用的记录标“共同记录”。已内嵌在本栏的记录不另列“相关时间记录”按钮，跨栏引用仍可跳转。

### 测量、处理、重新处理日志

测量、数据处理和重新处理各按实际工作新增日志，直接归入对应测量子栏，不再为每次处理套同名阶段壳。逻辑线只提炼论证并引用日志，不重复存实验细节。原始数据、脚本和处理文件留在实际目录，日志串起来源、过程与结果；处理结束后用现有 projects entry-add 新增记录。

处理日志按材料记录：输入数据路径及对应测量日志；方法、假设、参数和单位；脚本路径及可识别版本（没有版本号时写当次副本或哈希，不编造）；输出图表/文件位置；结果、验证、限制和未解决问题。评价与讨论明确作者和日期。发生日期是实际处理日期，不拿测量日期代替；未知就留空。正文无需机械填满，没有的信息不用写。

重新处理另开日志，关联原测量和旧处理日志，说明为什么重做、改了什么、结果差别；不覆盖旧版历史或原始数据。自动处理步骤可配置 log_requirement:{project_id,parent,links:[原记录或上下文日志ID]}（不是新增日志类型，也不是运行授权）。用 projects entry-add 时指定同一 project_id、parent，work 含当前任务 ID，links 含约定记录；已有测量日志时也关联它。当前没有测量日志的计划只能作为上下文，不冒充实测记录。程序完成检查要求实际非空日志、正确归属及关联；缺日志则 waiting_user，不释放后续、不自动重试。require_outputs 的分析文件仍须交付，FRAMEWORK.md 本身不能充当分析产出。程序不检查每个科学字段是否可靠，也不证明拟合或结论正确，助手须实际核查并留下边界。

单条记录可使用以下轻量格式，按材料删减字段：

```markdown
### T-YYYYMMDD-NN 简短标题
<!--node {"date":"YYYY-MM-DD","date_confirmed":true,"links":["相关节点或记录的 id"]}-->
- 发生时间：日期／范围／待确认的依据；记录时间：日期及必要时区（机器读的值是上一行的 date，两处要一致）
- 当时做了什么或怎样想：保留具体经过、结果、问题或计划
- 样品、条件与数据：有就填，没有不写
- 当时的判断／下一步：仅记录当时实际提出的内容
- 后续更正：后来怎么改了（关联的 id 写在上面的 links 里，不另写“关联”行；性质如仿真、计划需要区分时在正文里直说）
```

### 条目编号

- 格式 `T-YYYYMMDD-NN`。日期取**首次写入当天**（America/Chicago）；发生日期另写在 `date` 字段里。NN 在同一项目、同一日期内从 01 递增，超过 99 就继续写 100。
- 追加记录用 `projects entry-add`，编号由程序分配；`parent` 指定 `type=timeline` 内的主题或子板块 ID，记录直接归入那里。不指定则追加到日志根部，页面显示“尚未归入主题的日志”，不要从链接自动猜归属。手写条目时才先跑 `projects framework <项目id>` 取 `next_timeline_id`。
- 编号一经写出不改、不复用。改标题、移动条目、核实或更正发生日期都不动编号。
- 跨项目引用带项目 ID，如 `graphene-thz / T-20261006-01`（程序目前只校验本项目内的引用，跨项目写法会被当成不存在的记录，需要时写成文字说明）。
- **同一项目的 FRAMEWORK.md 一次只由一位助手写**，另一位只审阅；命令写入前会重新读文件，但不替两位同时改正文做合并。

## FRAMEWORK.md 的结构（程序读写，看板直接读它）

文件是**研究内容的唯一权威记录**：板块嵌套、正文、历史日期与证据关联都在这里，`projects/catalog.json` 不存框架节点。**当前操作步骤及执行状态唯一存在 `work/queue.json`**，不在正文再记一份当前状态；框架页面在对应时间日志主题内展示并操作关联事项，不另设“当前执行”大板块。研究说明、历史正文和操作步骤在主题内分区，不混写。服务端读取逻辑的改动要重启看板才加载。

- **板块就是标题层级。** `## ` 是一级板块（例如项目说明、逻辑组织、时间日志；个数和名字不预设），`###` 到 `######` 是嵌套小节，最深六级。AFM、STM、Raman 等具体测量、制造批次或排障可以在日志主题下分组并带研究标记；逻辑线只组织它们对论证的贡献与证据缺口。
- **结构化字段在标题的下一行：** `<!--node {...}-->`，单行 JSON，页面里不显示。字段都可省略：
  - `id`：小写字母、数字、连字符。要带状态、被引用、被点名推进或上传文件的节点必须有；时间记录的 id 就是标题里的 `T-…`，不重复写。
  - `type`：只用于一级板块。`info` 是说明性板块（合作与分工等，里面不带状态）；`logic` 是研究论证地图，不放试错尝试；`timeline` 是研究日志（以主题过程树分类，T- 记录嵌在对应主题或尝试下，同一父节点下的记录按日期／相对先后排序，整份文件至少有一个）。
  - `summary`：折叠时显示的一两句话；详细内容写正文，不写进 summary。
  - `kind`：研究节点的性质。`milestone` 阶段或项目（四种研究标记都可用）；`attempt` 日志主题中的一次已发生尝试（批次、制备、排查），只能标完成或失败，不能放在 `type=logic` 下；未做的具体事登记成 `work` 步骤。`info` 说明节点（动机、解释、参数），不带状态也不给“＋ 状态”；已有状态需先清除才可改成 info。时间记录不用 kind。
  - `status`：`done` 完成、`doing` 正在进行、`failed` 失败、`open` 未开始／待定义。`open` 必须在 `note` 里写明是哪一种。`status_date`、`history`（`[日期, 原状态, 新状态, 原因]` 的追加记录）由命令维护，不手改。
  - `date`、`date_confirmed`：发生日期，`YYYY`、`YYYY-MM`、`YYYY-MM-DD`，或用 `/` 连接的范围；不知道就不写。只有用户确认过才写 `date_confirmed:true`；上传日期、文件修改时间不能代替。
  - `after`：只用于没有 `date` 的时间记录，填它应排在哪条记录之后的 `T-` 编号（用户说“在某事之后”但不记得日期时）。记录仍留在所属主题内，显示“在某条之后，日期待补”；排序键只用于主题内排序，不当作发生日期，更不推出同月。既没有 date 也没有 after 的记录仍在主题里显示“日期待补”。补上 date 后 `after` 自动清掉，不改变所属主题。
  - `links`：本条目指向的其他 id（逻辑节点或记录）。反向的“被引用”由程序算，不要两边都写。
  - `corrects`：只用于时间记录，写这条后来的记录更正了哪些更早的条目（编号数组，只能指向更早的记录或任何节点，不能指向自己或更晚的记录）。旧条目一字不改，“已被更正”由程序从这里反向算出，在 `outline` 索引和 `search` 命中里标出。它不表示整条作废：新记录的正文要写清更正了什么，读者据此判断旧条目哪部分还能用。新数据代替旧数据、新解释代替旧解释、新方向代替旧方向，都用它；写 corrects 的记录，开头第一句写明替代的是数据、解释还是方向，旧条目哪部分不再采用、哪部分仍有效。后来的助手靠这一句和索引里的“已被…更正”决定做哪个、不做哪个。corrects 管不到 work 队列里挂在旧方向上的任务，那些要另行处理。失效只来自这样的显式声明；文件哈希只能证明内容没被改，查不出一份旧资料是否还成立。
  - `work`：与这条研究记录相关的任务 id（历史与执行的关联，不是另一份操作状态）。当前步骤用事项的 `plan_node_id` 指向对应日志主题、子板块或记录，页面在该节点下读取步骤，不复制状态到正文。未绑定日志节点（包括仍绑逻辑问题）的事项显示在时间日志内的“待归入日志主题的步骤”，不自动猜归属，也不隐藏。
  - `files`：看板上传的资料，由页面维护。
- **正文是 meta 之后的自由 Markdown**，直接改文件即可。各命令对正文的影响：`entry-add`／`node-add` 新建节点时写入给定的 `body`；`node-edit` 的 `content` 按提交的内容改写正文；`node-set` 不改正文，只有当日志的日期实际变化时才在正文末尾追加一行“日期更正”（同时撤销旧的 `date_confirmed`，除非本次重新给出）；`node-status`、`node-link` 只改节点的 meta 行；`node-edit` 的 `delete` 连同子树正文一并删除（须确认、先备份）。普通文字勘误可直接改原文，保留历史的整理也可以改；不允许的是悄悄改变事实或抹掉记录。正文里**顶层**的 `- 标签：…` 条目（含缩进的下级内容）会按标签收进折叠栏，其余留在正文，显示分栏不改原文：`用户评价`（只有评价；`用户说明`是用户讲的事实或理由，留在正文）、`助手备注`（也认 `助手评价`、`助手核算`、`助手解释`、`Claude…`、`Codex…`、`我对……的理解`；署名和日期写在条目里，如 `助手备注（Claude，2026-10-07）：`）、`讨论`（指向对话，不复制全文：写 `chat:<会话id>#<任务id>`，会话 id 取 `.runtime/agent/sessions.json` 里的会话 `id`，任务 id 取该轮用户发言的 `task_id`，可省；页面把它显示成“原对话 ↗”，点开会话并滚到那一轮，会话已删除时给出提示。助手备注的署名只认标签里写明的 Claude／Codex，没署名的页面标“作者未核实”，不要凭印象补署名）、`缺项`、`来源与性质`（也认 `来源`、`性质`）、`发生时间`／`日期更正`（日期依据）、`关联`／`后续更正`。事实、观测、操作和解释写在这些标签之外；评价、备注、缺项别混进事实句子里。**没有 meta 的标题**是普通小节（页面里是折叠的说明文字），不带状态、不能被引用。
- 正文里提到的 `T-…` 编号必须真实存在，`projects framework` 会逐个核对；链接里的 id、任务 id 同样核对。

### 状态怎么记

- **操作坨坨改的是 `work` 的具体步骤**，不是解释文字或历史段落。四种视觉状态对应 `done`、`active`、`failed`、`queued`；依赖等待和 `waiting_user` 另写明确文字，不伪装成已开始。操作步骤区只汇总步骤，不自动判定研究结论；日志中的父阶段仍可由用户明确确认标绿，不由子项推出。“这批天线制备完成”不等于天线研究完成。
- 已有 FRAMEWORK 的 `status` 是手动研究标记，不用于触发操作或作为任务状态副本。绑定了执行步骤的记录不再同时维护一份执行坨坨；说明性文字不带操作状态。
- 执行流程用 `work add` 登记，每一步带 `dependencies`、`project_ids`、`plan_node_id`。默认不自动运行；明确获授权的助手后续步骤才带 `auto_start:true`。用户实验步骤不可自动运行。前置全为 `done` 才能开始或完成；就绪由程序计算。
- 测量完成时用户在页面上只填**留言**（`handoff`），数据存放位置写在留言里，无需预先指定；留言不能为空，助手步骤拿到后先确认位置真实存在再处理。助手交付文件的步骤设 `require_outputs:true`：位置存在、留言非空才能完成，**这里只检查交接是否完整，不证明数据科学正确或路径内容是原始数据**。
- 现有 `agent.drain` 将就绪步骤以原 work ID 纳入会话，读前置的留言及数据路径交给指定助手；重复心跳不重复派活，失败/缺交付转为失败或等待用户，不自动重试。处理交付完成后才释放邮件草稿步骤；只起草，不对外发送。
- 研究标记若保留，跟着具体的板块或记录走：父板块的颜色**不由子项推出**，完成一项测量也不等于科学解释成立。说明性板块（`type=info` 之下）不带状态。
- 研究标记按用户的话记：用户说完成、失败可照记并注明来源；助手不凭材料替用户写下“完成”“失败”，也不把“机制成立”写成已确立的成果。助手可以基于证据提出、检验或反驳解释，写成署名的评价，不冒充用户认可。助手追加记录时默认不带状态；操作计划登记为 `work` 步骤，不再同时给时间记录标“未开始”。
- 离开“完成”或“失败”等于推翻一个已记的结论，必须写原因（程序会拒绝没有原因的修改）；其他变化原因可写可不写。每次变化都进 `history`，改回（如红改回黄）同样留带日期的原因。
- 页面上点开状态坨坨即可修改：要原因或说明时就地问一句。操作步骤整合进时间日志，在 `plan_node_id` 对应主题或记录下显示独立步骤区；不插入逻辑线、不混进历史正文、不另设“当前执行”大板块。有未完成步骤的主题及祖先默认展开。步骤灯只改 work：前置未完成时不能进行中／完成，完成要留言，重开完成／失败要原因。

### 项目页便捷编辑

- **新增只留三种入口：子栏、日志、操作步骤。** 子栏默认不带灯，新增面板只提供“带状态灯”开关（开启存为 milestone），不让用户在说明／阶段／尝试三种类型中必选；原 kind 和状态不迁移，尝试可以直接记日志。说明性祖先禁止研究状态时开关禁用并解释；不改变已有状态规则。
- **详情按显示收成三组，不改正文标签：** 评价与讨论（保留各自身份、署名、日期、作者未核实及原对话入口），来源与更正（仍明确保留观测／仿真／解释／计划等性质），缺失信息。逻辑线的缺项显示为“还缺什么证据”，日志里显示“待补记录”；两者不自动生成任务。关联链接和理由另保留；空组不显示。已被后来回答的缺项，助手可以挪到“来源与更正”并保留原话和日期；不因显示合并而删除或改写原文，删除信息才需用户定。
- 时间日志主题、子栏或单条记录内的“＋ 操作步骤”直接归入该节点，填标题、说明、负责人及本项目现有前置。默认 user、queued、auto_start:false，唯一写入 work；保存只登记，不唤起模型、不对外发送，也不修改现有执行链。自动执行需另行明确配置；不能把选了助手负责人当成自动运行授权。页面接口 `/api/work/new`、`/api/work/add` 复用 enqueue，保存时重验日志归属和前置，不允许无效或跨项目依赖。

- 标题旁“编辑”直接修改本栏标题、摘要和原文（不包含子栏），不从分栏后的显示结果反推正文。展开后可“＋ 子栏”“＋ 日志”；大板块入口在框架标题旁。这些入口和删除、步骤编辑只在项目页的“编辑栏位”模式下显示；该模式还提供拖动手柄，重排栏位和改归属靠拖动（节点用 `projects node-edit` 的 `move`，可带 `before`／`after` 指定同级位置；步骤用 work 的 `/api/work/move`）。
- 日志只放时间线，移动只在同一内容线内并携带子树；新子栏默认不带灯，可明确开启阶段灯，不自动赋状态；旧尝试类型保留，新增失败或试错直接记日志。状态和任务仍走原有工具；日志编辑可补日期和确认情况，重用 node-set 的日期更正规则，与正文原子保存。改日期撤销旧确认，除非本次明确重新确认；旧日期依据保留并追加更正。
- 保存经过唯一写入入口并检查文件版本与结构；正文代码围栏须闭合，不会因代码块吞掉后续板块。文字编辑遇到无关栏／状态变动时重新读取并重试一次；本栏文字或日期变了，展示最新版并保留草稿，由用户核对后更新基线再保存；不自动覆盖。结构动作仍拒绝旧版本。轮询不刷新掉编辑面板，取消未保存修改要确认。
- 每次有效写入前保留完整旧文件于 `.runtime/framework-edits/<项目id>/<旧版本SHA256>.md`，仅作恢复依据，不是权威副本。实质更正应追加说明，不能悄悄重写历史。
- 工具：`projects editor <项目id>` 取原文节点、`revision` 和带保存时间／路径的备份清单（保存时间不是实验日期）；`projects node-edit <JSON文件>` 使用 `{project_id,revision,action:content|fields|add-node|add-entry|move|delete,id?,parent?,title?,summary?,body?,kind?,type?,confirm?,fields?:{date?,date_confirmed?,after?}}`。fields 仅用于日志日期；content 可附 fields 一次保存；不更改状态或任务。正文不能加入框架级 `##`～`######` 标题或 node 元数据，结构用新增／移动。备份可在编辑面板查看，无一键恢复，不能直接覆盖后续有效改动。
- 操作步骤旁“编辑步骤”改标题、说明、负责人、留言和前置依赖，唯一写入 work；保留 ID、状态、产出、归属及自动执行设置。`work editor <id>` 取步骤与 revision，`work edit <JSON文件>` 用 `{id,revision,action:content|delete,title?,goal?,handoff?,actor?,dependencies?,confirm?}`。拒绝旧版本、循环、自依赖、失效前置、执行中／已派给助手的修改；已完成步骤不能依赖未完成步骤。
- 用户明确要求时可点“删除本栏”或步骤“删除”，显示范围并勾选确认；不由助手因内容粗糙而自行删原资料。框架 `node-edit` 的 `action:delete,confirm:true` 删除子树前备份，自动解除 links、corrects、after、旧步骤节点绑定、直接来源引用及当前节点指向；其他正文保留，指向被删日志的本地链接转为普通文字，裸编号标为已删除记录。不删除操作步骤或磁盘附件，不改变步骤状态与前置依赖，不删最后一个时间日志板块，也不复用旧 T- 编号。步骤自身的删除行为不变：拒绝执行中及被依赖的事项，保留后台 cancelled/deleted_at、历史与交付文件；旧队列备份在 `.runtime/work-edits/<SHA256>.json`。不新增模型调用或自动派活。

### 命令

都读一个 JSON 文件（路径作参数），只改目标几行，写完重新解析，若引入新问题就整体不写，所以失败时文件原样不动：

| 命令 | JSON | 说明 |
| --- | --- | --- |
| `projects entry-add` | `{project_id, parent?, title, date?, date_confirmed?, after?, body?, links?, corrects?, work?, status?, note?, summary?}` | 在日志主题或子板块内追加记录，返回编号；parent 不得是逻辑节点、记录或最深六级标题；不指定则待归类 |
| `projects node-add` | `{project_id, parent \| null, id, title, body?, summary?, type?, kind?, status?, note?}` | 新增板块或子板块；`parent` 为 null 是新的一级板块 |
| `projects node-status` | `{project_id, id, status: done\|doing\|failed\|open\|none, note?, reason?}` | 改状态；`none` 清除；规则见上 |
| `projects node-link` | `{project_id, from, to, rel?}` | 在 `from` 的 links 里加上 `to`；`rel:"corrects"` 则写进 `from` 的 `corrects`（见上），`to` 不动 |
| `projects impact <项目id>[#节点id]` | | 只读：列出已被更正的条目，和直接引用它们的节点（`referrers`：links 或正文提到编号，是复核候选，不是已证实受影响；`also_cites_corrector:true` 只表示它也引用过更正者，不证明已复核；复核完一个引用者，就用 `node-link` 把它关联到更正者，它之后会显示为 `also_cites_corrector:true`，名单靠这个动作收敛，程序不另存“已复核”状态）；不带节点 id 时另列 `note_only`：正文写了「后续更正」但没有记录声明的条目，可补 `corrects`。只算直接依赖，不替人判断是否受影响，不写任何标记 |
| `projects search [项目id#]<查询词>` | | 只读全文检索（FRAMEWORK 节点／记录和项目里其他 .md，不含 STATUS.md 与 FRAMEWORK 快照）。与会话检索 `agent search` 共用 `automation/text-match.mjs`：先要求全部词都出现；凑不齐（常是凭记忆整句来问）就按字词片段近似匹配，结果 `mode:"near"` 并带近似度，只是候选，要自己看片段判断。不是语义检索，换说法碰不到字面片段时仍找不到。每次现扫文件，无索引无缓存。命中带 `corrected_by`／`correction_note` 时先读更正再引用，命中不会被隐藏 |
| `projects node-set` | `{project_id, id, date?, date_confirmed?, after?, summary?, kind?}` | 改节点的简单字段，补日期就用它；`null` 删除该字段；设了 `date` 会清掉 `after`。仅当日志的日期实际变化时，才清除旧的 `date_confirmed`（除非同时给出）并在正文末尾追加一行“日期更正”；日期没变、或只改 summary／kind／after 时不动正文。不改状态和关联 |
| `projects framework <项目id>` | | 只读检查，并给出今天下一个可用编号 |

`framework` 检查：重复 id、非法状态或日期、`open` 缺说明、说明性板块里的状态、links／任务 id／正文里的编号指向不存在的对象、页面会露出字面 `**` 的行、没有 `timeline` 板块。有 `problems` 就改完再交接；它不替代人工核对出处、日期和数值。

### 显示规则（用户已定，不要加回）

- 逻辑组织没有“当前步骤”“设为当前”；不显示“详见 FRAMEWORK.md#…”、“下载框架原文”、项目卡片上的内容线计数和“可放图片、图表…”提示；原文只在「项目文件」留一个入口；图片是固定高度缩略图，点开看大图。
- 没有 id 的小节（如“研究背景与整体联系”）是折叠的引言，不做成卡片。
- **阶段与日志只统一展示，不自动合并。** 内层日志用轻量详情行；阶段／尝试／说明子栏恰好只有一条直接日志、没有子栏及操作步骤时，打开父栏默认露出日志详情。用户手动折叠优先，刷新不记录隐藏子项的默认开合。内外 ID、原文、状态、编辑、附件及引用各自保留；文字编辑只留标题旁一个入口，附件在各自操作行标明“给本栏添加附件”或“给本条日志添加附件”；外层删除按钮标明包含几条日志，内层写“删除本条日志”，仍按原规则确认并保护。不要仅凭标题相似或父栏正文为空就合并／删除。
- **时间日志**直接展示按主题嵌套的过程树，不再用“按主题回看”外层折叠藏住主入口，也不按月份分组。T- 记录嵌在对应主题或具体尝试里，仍是一行日期、标题、编号；未知日期不移出主题。最初的阶段骨架单独收在阶段概览，不与详细实验并排当同一层主模块。展开后正文在前，补充详情收成三组折叠（评价与讨论／来源与更正／待补记录），空组不显示；每条记录的正文只有一份，其他入口引用 ID。
- **逻辑节点**展开后：研究动机／问题、已有证据、内容关系、证据边界与证据缺口，评价与来源折叠；“相关时间记录”只提供证据出处跳转，不铺试错过程，也不展示操作步骤。**日志主题节点**保留过程树、阶段／尝试标记、详情与讨论，并在独立步骤区读取当前 work；每项步骤只在所属日志节点显示一次，历史正文不记第二份执行状态。
- **原文里的链接**在页面里只剩文字（相对路径和 `#` 锚点在页面里点不开）；需要给读者的出处要写成文字，不能只靠链接。
- **加粗：** 结尾 `**` 前是标点、后面紧跟文字时，页面会露出字面 `**`。写成 `：** 后文`，或把标点移到 `**` 外面。

## 新对话看到什么

项目关联默认只提供项目身份和资料入口，不自动加载研究目录、历史索引或执行状态。资料未预读；由 agent 按当前任务取所需内容。普通会议邀请不因关联有 FRAMEWORK 的项目就通读研究资料。明确绑定的阶段仍附该阶段说明和文件入口。

- 未绑定项目的普通对话也提供同一读取入口；先用 `node automation/run.mjs projects list` 找项目 ID。以下命令都从办公室根目录运行，不必 cd 到项目文件夹；默认不整份读取 FRAMEWORK.md 或递归通读项目目录，确需全项目梳理或编辑原文时可读原文件。
- 有具体问题时，可先用 `node automation/run.mjs projects search "项目id#关键词"` 看命中，再选相关节点读取；片段和摘要是导航，不替代引用所需的证据原文。
- 需要研究背景时，用 `node automation/run.mjs projects outline 项目id` 取各层节点的标题、完整摘要、类型与状态，以及所有历史日志的精简索引；包括嵌套在时间线中的 info／实验方案，不按“最近几条”遗漏旧主题。它是导航，不是已经读过的正文。
- 根据当前工作成组选择节点，用 `node automation/run.mjs projects read-nodes 项目id#节点ID,节点ID` 读取完整原文和子节点；返回来源文件、行号与版本。无 ID 的标题可按索引给的行号直接读文件。执行事项按需用 `projects context 项目id` 读取。
- 时间线主题节点的 `summary` 写现状（做到哪、卡在哪、最新结果，一两句，指向最新日志编号），有新进展时顺手更新；数据处理和分析类主题开头保留“目的：…”一句（见 RULES），更新现状只改后面；摘要不替代方案、经过、用户判断或数据。
- Methods、文件和历史日志正文按需读取。原始资料或执行状态变化时给续接会话发简短失效通知，需要时重读，不自动塞回整份背景。

## 缺口与已完成事项的登记细则

   - **缺口与待办：** 发现或用户指出证据缺口，先记在对应逻辑节点并保留来源，不等于授权执行，不替用户编造待办。用户提到要做某项工作时，助手可直接用 work add 登记带 project_ids、plan_node_id 的具体步骤；默认 auto_start:false。用户当下叫助手做的分析不需要再授权；只有新增无人值守的自动派活（`auto_start:true`）才另须明确授权。用户当时的决定/计划可用 projects entry-add 记入对应日志，links 关联逻辑节点，work 关联任务；不重复维护执行状态。不复制缺项正文，不猜截止日期，没有 due_at 就不填。
   - 不通读所有缺项批量生成任务（这是防批量误派，不是限制个别明确的事项）。已经获授权的事项做完或放弃时，用 work update 更新任务，并追加有日期的经过日志，关联原条目和任务。需要处理日志的事项先交日志再标 done，不能先放行后补记录。原条目保留不删、不改执行状态，以 work 为准。
