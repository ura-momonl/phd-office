# 科研项目整理

把项目整理成找得到资料、分得清说明与经过、看得出依据与变化的工作台，不预编论文故事。先读现有框架和相关资料；在已授权目标内，本地、可逆的整理与分析直接做。通用权限与行动边界见办公室 `AGENTS.md`。

## 放哪里

| 内容 | 去处 | 怎么放 |
| --- | --- | --- |
| 对项目有长期帮助的实验数据、仿真与分析结果、研究判断和当时的计划，包括有用的失败结果 | **项目日志** | 记录发生日期、条件、结果及对应资料，保留以后研究和分析用得上的内容。 |
| 操作过程：测试或实验方案与步骤、文献调研和数据处理的做法 | **说明子栏** | 过程放子栏，结果才放日志。见下面“过程放子栏”。 |
| 主题介绍、方法原理、参数含义、共用条件 | **说明子栏** | 有必要才写；可容纳真实日志，说明只引用记录或提炼摘要。 |
| 当前理解、内容关系、证据边界与缺口 | **逻辑组织** | 引用来源与日志，不搬运完整经过；允许稀疏、未定或有竞争解释。 |
| 用什么测什么、读数与单位、数据处理约定、仪器设置、坐标与编号 | **逻辑组织里的 Methods 节点** | 像论文的 Methods，只供助手接手工作用，不指导写文章；每条一两句，指向详细日志或文件，约定变了就改这里并留日志。 |
| 当前待办、负责人、执行状态 | **`work`** | 用户要做的事，以及助手根据项目进度自己判断该做的事，都由助手登记，不等用户开口。证据缺口可以成为助手的读、算、查步骤；不能当作用户实验或对外动作的授权。 |
| 邮件往来、约会、会议安排等杂项 | **项目页「关联资料与杂事」** | 项目关联的邮件、未绑定研究节点的 mail/misc 步骤和日历事项自动在这里显示，原记录仍由各自模块维护；额外的事务笔记用 `projects related-add` 保存，用 `projects related` 读取，不重复抄已有记录。默认不进逻辑线或时间线；只有对研究有明显作用的数据、判断、方法或研究计划才提炼入研究两条线并引用原记录。 |
| 没有项目长期价值的临时操作、排错、状态修复、补附件、改标题、归类、排版等 | **普通 `logs/`／交接** | 不因操作属于某项目就写项目日志；产生有用的研究结果时，只把研究内容记入项目日志，操作记录引用它。 |

**先按对项目的长期帮助决定是否进入项目框架，不按有没有数字或图片判断。** 有研究价值的内容中，说明回答“这是什么、怎么理解”；日志回答“何时做了什么、条件和结果如何、当时怎么想”。具体实验数据与结果图随日志；通用方法说明或原理图可放说明。归属由助手结合内容判断，程序不因步骤挂在项目或日志主题下就强制新增项目日志。

## 怎么放

- **按内容开栏，不凑模板。** 值得独立命名和查找的主题才开子栏；日志可以嵌在子栏内，没有介绍就不写，没有内容不留空模板。按主题组织，日期放在记录上，不强制栏数或层级。
以下三条是用户的习惯，靠助手自觉照着做，不是程序强制；遇到特殊情况按用户当下的意思处理。

- **时间线按时间顺序往下排**（用户 2026-10-11 提）。同一父节点下的子栏和记录大致按发生先后排，新内容接在后面。`projects node-edit` 的 move 和新增都放在父栏末尾，新建或挪动后看一眼顺序。补录的内容如果比已有板块或记录发生得更早，新建后立刻用 move 的 `before` 放到它前面，不留在末尾（用户 2026-10-17 提：先做的测量被排在后面）；发生日期不明时，按用户或材料给出的先后排。子栏挪了，里面的操作步骤的 `plan_node_id`（和带日志要求的 `parent`）也跟着改。
- **过程放子栏，结果放日志**（用户 2026-10-14 提）。方案、步骤、检索和处理的做法这类“怎么做”，写在该主题的说明子栏；日志记做出来的结果和细节（条件、数值、结论、文件）。还没做的方案先放子栏，做完再在子栏下追加结果日志。用户口述的“当时计划”是历史，照旧记入日志。
- **新建操作步骤默认“未开始／待定义”**（用户 2026-10-14 提；2026-10-15 起按操作对象区分）。用户实验和助手对用户的提议一律 `status:open`，由用户接受后才变成待办、开始、完成。助手自己的本地、可逆步骤（分析、检索、起草、维护框架）由助手建立；用户已直接交办的工作和已授权操作的后继按已有任务授权推进。助手自行派生的新工作建立时就要写清来源（哪个未决问题或事件）、会改变什么决定、交付物，能否直接 `queued` 由程序当前的自主等级决定（用户 2026-10-15：权限从保守开始、逐步放开，提示词本身不保守）；等级未放开或程序拒绝时，先建 `open` 并写明入队条件，不绕过。有先后的步骤用 `dependencies` 串起来，前置条件（如先 wire bonding）单独成一步。
- **项目速览（项目说明）只由“项目推进”那一轮维护，只写固定背景。** 内容限于：项目的研究问题、合作方与分工、接手关系、主要资料位置、样品对应。不写进展、结果、状态、旧分析的去向，这些归日志、`work` 和状态页。项目推进（一个日志主题下的步骤全部完结后由 Codex 执行，会读本规则和项目全文）读到速览时，对照来源步骤的交接和日志：固定背景有新事实就补一行，写日期和来源；越界的进展行直接删；没有新事实就不动。其他助手处理步骤时不改这一板块，发现新的固定事实写进自己步骤的交接里，由推进那一轮据此更新。
- **一处记录，其他地方引用。** 正文和附件各有一处权威位置，其他入口引用 ID 或路径。文件可留在原位工程或数据目录，不必搬进项目，但应在对应记录中写明路径；具体测量的附件入口归对应日志，共用资料由共同记录或说明引用。
- **资料带说明。** 写清是什么、适用样品与条件、列名及单位、具体来源、原始／转录／处理结果，以及与哪次记录对应。数值表优先用可引用的数据文件，不拿截图或正文大表代替；格式、预览和来源副本是否保留按用户要求，不把一次偏好变成通用硬限制。
- **日期分清。** 补录区分发生日期和记录日期；发生日期可写日期、范围、相对顺序或待核，不拿上传日期、文件修改时间、图上日期直接代替。
- **数据处理和分析要先有目的，写在母栏（步骤所在子栏的上级栏）的正文开头，子栏不重复。** 内容是“要回答什么问题、判据是什么、要交什么”，来源写到具体的日志编号或页码，摘要以“目的：”开头，更新现状时保留这句。目的段的写法固定：正文开头一行 `**目的…**`，下面紧跟 `- ` 列表；程序会沿上级栏找最近的这一段，自动放进该栏下步骤的提示词，子栏和步骤说明都不必引用或重复。母栏没有这段时，接手处理的人先从项目历史（图计划、用户说明、逻辑栏）自己找出目的，按这个写法写进母栏正文，再开始处理。
- **研究结果可追溯。** 需要长期保留的测量、分析和重处理结果记入项目日志。处理记录关联原测量，写输入、方法与参数、脚本及可识别版本（如当次副本或哈希）、输出、结果与限制；重新处理关联旧版，说明变化，不覆盖旧结果。按已有材料写，不编造缺失字段；临时检查和操作细节记普通 `logs/`。

## 什么不放进研究正文

- 不把整理框架的讨论、界面与助手操作、聊天流水账写成研究经过；但保留真正的研究讨论、失败、当时的猜想与计划。
- 不重复维护 `work` 的当前执行状态；历史日志里的“当时计划”保留，不冒充今天的待办。
- 不把界面占位数据当研究内容，不把仿真当实测、文献性能当本项目成果。科学假设可以直接写。
- 不留空模板，不重复维护同一正文或附件；需要多个入口时引用，具体见上面的“怎么放”。

## 可信与协作

- **框架里每句话要让后来的人做对一件事或避开一个具体错误，否则不写。** 日志写事实和结论，不写免责。本条管写进框架、日志、图注、摘要、说明的文字；聊天回复和交接里的“没验证什么”照 `help handoff` 写，不抄进框架。
  - 不写（用户 2026-10-13、10-17 两次要求）：
    - 对自己工作或用户数据的免责：“未核原始记录／仪器导出”“仅供参考”“不据此认定”“不能当可重复结果”。用户提供的数据就是原始数据，核对仪器导出是用户自己的工作。
    - 对早期、粗测或后来被重测的实验的整体评语：“粗糙”“不可重复”“结果不可靠”。用户自己这么说时，只记一条“用户判断：…”，不改写成框架的结论。
    - 没有补法的缺项：“尚未记录”“含义未记录”“待核”。缺的东西若会让后来的人做错事，写成“缺什么 + 怎么补”；否则不写。
    - 说明这次整理范围的话（“只收…不收…”）、泛泛的缺项清单、重复上文或别处已有的来源与提醒。
  - 要写：早期或有问题的实验也按内容如实记，先写做了什么、测到什么、条件和数值，再用一句具体事实写限制（例：“角度只有 5 个点，另一半按反号补全”），不写“能说明什么、不能说明什么”式的总评；观测、仿真、用户解释、计划需要区分时直接标出；具体缺什么及补齐办法；有来源的决定。来源只在需要追溯时写具体出处（图、文件、对话）。
  - 保存前自检：`grep -n -E "未核|未记录|尚未|待核|仅供|不据此|不能当|粗糙|不可重复" workspace/projects/<项目id>/FRAMEWORK.md`，每处命中都删，除非它写明缺什么并给了补法，或是标了“用户判断：”的用户原话。
  - 给本文件或其他规则加条目时，写清“什么情况下做什么”；“尽量”“注意”“适当”这类无法判断是否做到的话不写，已有规则覆盖的不再换说法重述。
- **摘要可更新，历史不抹掉。** 普通文字勘误和归类直接改；改变事实、来源或解释的实质更正追加带日期的记录，关联旧条：新记录用 `corrects` 声明更正了哪些更早的记录（命令见 TOOLS），旧条目不再改写，程序据此在索引和检索里标出“已被更正”，`projects impact` 列出直接依赖它的节点供复核。原始资料的删除或覆盖由用户明确决定，分析在副本上做。
- **研究标记按用户的明确判断记。** 助手评价署名（Codex／Claude）和日期，不冒充用户认可；子项完成不推出父项完成或机制成立。
- **同一项目的 `FRAMEWORK.md` 一次只由一位助手写**，另一位只审阅。已有框架原位更新，结构不在 `projects/catalog.json` 的 `plan` 里再存一份。

## 操作与验收

改结构、跑命令、处理字段或显示问题时，读 [FRAMEWORK-TOOLS.md](FRAMEWORK-TOOLS.md)；日常内容整理不用通读。追加日志用 `projects entry-add`，编号由程序分配。

写完用 `projects framework <项目id>` 检查结构与引用，再核对实际改动的来源、日期、数值和文件入口；涉及显示时检查实际页面。验收只问：**资料找得到吗？说明与经过分清了吗？依据与变化看得出来吗？** 已验证与未验证的范围写在回复和交接里（按 `help handoff`），不写进框架。
