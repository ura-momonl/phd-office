## 边界

- 邮件判断不能将事项标为完成；用户点“已处理”或助手在明确来源链全部办完后写 resolved 可结案，均留可撤销记录。审批结案不等于执行授权。
- 凭据按 AGENTS.md 使用；敏感值不输出到聊天、日志、交付物。
- 示意内容不能当作真实目标或进展；不编造实验结果。
- 工作习惯与自动化成本取舍以 `AGENTS.md` 为准；预算提醒不是裁剪必要上下文、减少必要核查或限制对话工作能力的理由。
- 同一文件避免两个 AI 同时改写；接续工作读当前内容与本文。

## 运维与已知的坑

- 服务常驻：服务端代码在启动时加载，前端文件每次现读。改了服务端代码须重启，`Open-Workbench.cmd` 会比较 `/health` 的 `started_at` 与源码修改时间并重启（有 agent 任务在跑时只警告）。
- 测试直接读写模块所在目录，**不要在真实项目里跑**。用 `node scripts/run-tests.mjs`：它自动建一份脱敏的临时副本（空任务、空邮件库、虚构采购样例，模型无法启动），在里面跑三组测试后删除副本，生产不受影响；加 `--keep` 保留副本供查看。
- 新增计划任务或启动方式后检查真实 Windows 窗口，`scripts\Probe-Windows.ps1` 可采样弹窗。办公室现在走 WScript 隐藏入口，真机及隔离副本无可见主窗口；不要重新包一条独立的启动路径。其他终端启动方式是否闪窗应按实测判断。
- Codex 的调用方式保持原样：不按用途关闭它的内置功能、不做“精简档”。用户的决定：优化策略以系统设计为准，不迁就某个模型的 token、缓存或上下文特性；Codex 的 CAD 工具已由用户迁到各自文件夹，全局关闭。试过的精简档已整体回退（原因和数据见 CHANGELOG.md）。
- CAD 任务的调用方式（`agent/codex.mjs` 的 `codexLaunch`）：请求提到哪个软件，Codex 就在 `software/catalog.json` 登记的目录（`D:/cad-ai`、`D:/fusion-ai`、`D:/Altium-ai`）里启动，工具由该目录的 `.codex/config.toml` 启用，项目根仍可写；提到多个软件时以 Fusion 目录为主（Fusion 插件只能靠目录配置启用），其余用 `-c` 打开服务；没提软件则在项目根，工具全关。不要再写 `enabled=false` 的 `-c`，它会盖掉目录配置。Fusion 的服务是 `127.0.0.1:27182` 的 HTTP 端点，Fusion 360 没开时它报 0 个工具，属正常。模型在对话里能否实际调用这些工具尚未验证。
- 两个 AI 的接入是同一套约定：`agent/codex.mjs` 与 `agent/claude.mjs` 各一个文件，都导出 `invokeX(prompt,{mode,effort,onEvent,directory,signal,model?})`，返回 `{result,usage,model,sessionId,toolCalls,duration_ms}`；`mode` 只有 ask（无工具单轮）/work（对话轮，文件夹内全部权限）两种；都写 `prompt.txt` 与 `events.jsonl`、都记一笔用量、失败提示一致（`agent/native.mjs` 里的 STOP/EMPTY 消息和杀进程函数）。`agent/run.mjs` 的 `invokeNative(provider,prompt,options)` 只选 AI 并存 prompt。`model` 两边都可按次指定；Codex 不传时用 `codex_model`。邮件判断分两档，都走 Codex（`agent/mail.mjs`）：`mail_screen_model`（Luna，粗筛独立的小邮件，拿不准或涉及截止时间/项目/重复事项就返回 escalate）与 `mail_judgment_model`（Sol，处理规则已关联到未完成事项的邮件和被 escalate 的邮件），各自的强度是 `mail_screen_effort`、`mail_judgment_effort`；两档的决定合并后由 `Flow.apply` 一次校验写入，`automation_daily_calls` 按实际调用数计。新增第三个 AI 时照这个约定加一个文件即可。
- 数据备份：项目不在 git 里，`automation/backup.mjs` 由自动处理循环每个 UTC 日拷一份到 `.runtime/backups/<日期>/`（任务队列、项目/采购/文献/软件目录、会话、周计划、收件箱状态、草稿，邮件账本用 `VACUUM INTO` 取一致副本），保留 14 天，不调用模型。模型写错了数据，从这里取回。
- 窄窗口（≤600px）走移动端布局；≤900px 时卡片上下排列。

## 没验证 / 已知不足

- 新邮件在生产里的端到端去重、每日上限真正触达、判断失败提示的真实出现，都还没遇到过。
- 模型偶尔不按格式回复；卡片模式有回退到纯文本交接，回退频率未观察。卡片现在由 Luna/Sol 准备，格式遵从率未实测。
- 遗留一例重复事项（“完成 2027 年福利开放注册”与“核对2027福利开放登记是否需要操作”），需用户处理掉其一。
- 采购报价靠手填（邮件只读到正文前 700–3000 字，没读附件）；文献 0 篇；校园授权全文、Zotero、CAD/仿真实际执行尚未验收；Discord 未配置。
- 新的交接格式刚上线，agent 实际遵守的比例待观察。

## 怎样继续改进

先从用户的路径看：提出本周目标 → agent 推进 → 必要时进收件箱 → 用户选择 → 继续推进 → 验收与复盘。找出这条路径最妨碍自动化的地方，再考虑视觉优化；也可以指出哪里设计得多余。

从实际问题中选择最有价值的改进，直接实施并做与改动相称的验证。交付时简要说明改了什么、能省哪一步、如何验证，以及对准确性和模型调用的影响；区分已经观察到的问题和待验证的猜测，保留做得好的部分。细节不足只补读相关文件，避免扫描无关历史、vendor 或 node_modules。
